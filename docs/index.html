Three Claude Code skills · an explainer

Graph, Bakeoff, DAG: three ways to run agent work, explained like you're five

Split a job only when splitting pays. Test a new way of building before you trust it. Let nothing leave the machine until a person signs for exactly what is leaving.

An agent here is a model session that can read files and run commands. Fan-out means handing pieces of one job to several agents at once; fan-in means merging what they return.

The whole idea in one kitchen

Picture a busy restaurant kitchen. Each skill is one person in it.

The head chef

/graph

Looks at tonight's order and decides whether to split the chores among helpers. Most nights the answer is "no, one cook is faster", because helpers have to be briefed, and someone has to put their pieces back together.

The bake-off

/bakeoff

Two cooks bake the same frozen recipe. A taster who cannot see who made which cake scores both. After a few rounds, the winning way of cooking becomes the house method.

The recipe card

/dag

A card with checkboxes that survives a shift change, so the next cook picks up where the last one stopped. A manager signs exactly the plate that leaves the kitchen. Change the garnish and the signature no longer counts.

One meal can use all three: the chef plans, the cooks build, the card and the manager release. The rest of this page takes each person in turn, with the real mechanism under each picture.

Is "bakeoff" the right word?

For how it runs, yes. For what it decides, the better name is:

champion/challenger test

The house method (the champion) keeps its place until a newcomer (the challenger) beats it on a test both sides agreed to in advance. Then the newcomer becomes the house method. That is the decision /bakeoff makes.

The mechanics are borrowed from language-technology research, where a "bakeoff" is a shared-task contest: every team gets the same data, and a referee scores them on test data the teams never see (the SIGHAN 2003 bakeoff is one example). Donoho calls this setup the Common Task Framework in 50 Years of Data Science.

Names that sound close but mean something else

A/B test
Splits live users at random between variants. No users here, so the two sides are just called Arm A and Arm B.
Best-of-N
Keeps the best of many tries from one method. It never compares two methods.
Arena
Ranks entries from very large numbers of crowd votes.
N-version programming
Runs several versions side by side in production, with a voter choosing between their outputs.
Tool one

/graph The head chef who usually says no

The pictureBefore handing out chores, the chef asks of each step: does chopping the onions really have to wait for the oven? If not, two helpers can work at once. Then the chef checks that no two helpers need the same cutting board.

Under the hood: what /graph actually does
  • Fake edge testAt each "then", ask whether the next step reads the previous step's output. If not, the wait buys nothing and the two can run together. If no two steps are independent, there is no graph to build.
  • Reverse testFor each pair marked independent, name where each one writes: a file, a branch, an inbox. A shared target is a hidden edge. Fix it one of three ways: a separate workspace (a git worktree, a second checkout of the repo), put the pair back in order, or make the write idempotent (safe to repeat, so a retry cannot apply it twice).
  • A five-way gateNo independent steps, a small job, a person who wants to approve every step, or a problem nobody understands yet: each of those stops the plan and sends the work to one steerable session. Only work that is truly wide and independent goes on.
  • A priced bill before any agent startsThe realistic speedup, the total agent count across every axis, how many records reach the merge step, and a model tier for each kind of node.
  • Frozen rulesThe rules a node would bend to look successful are written into the spec, and no node may tune them.
  • An anchored verifierThe check reads ground truth that cannot argue back, like a test that actually ran. With no anchor, the result ships labelled UNVERIFIED.

Why the chef says no so often

Splitting is not free. In a 260-configuration study (arXiv 2512.08296), every multi-agent architecture scored below a single agent on SWE-bench Verified, a benchmark of real GitHub issues: Hybrid 2.1% lower, Centralized 3.1%, Decentralized 5.4%, Independent 14.9%. The same paper finds the effect depends on the task (large gains on decomposable work), so this is one data point, not a law. It is why a fleet has to earn its place.

The second reason is arithmetic. Amdahl's law says the part of a job that cannot be split sets a ceiling on the speedup, however many helpers you add. In the kitchen: plating is one person, no matter how many choppers you hire.

S = 1 / ((1 − p) + p/N) ceiling = 1 / (1 − p)

The /graph command's own worked examples: at p = 0.95 with 16 agents, the speedup is 9.1x, not 16x, with a ceiling of 20x. At p = 0.7 with 16 agents it is 2.9x, ceiling 3.3x. Below p = 0.7, /graph says plainly that merging and checking the lanes outweighs the time saved. In the author's log of five build plans, only one cleared that line (p = 0.75); the others ranged from 0.30 to 0.625.

Pros

  • Warns plainly that the graph is mostly overhead when p is below 0.7.
  • Prices the run first: speedup, ceiling, total agents on every axis, and fan-in width, all before any agent starts.
  • Planning costs only the main session's tokens, and a common outcome is keeping the job in one session (four of the author's five logged build plans fell below the 0.7 line).
  • Finds hidden edges (two steps writing one target) before they race.
  • A verifier must read an anchor; otherwise the result is labelled UNVERIFIED instead of passing as checked.

Cons

  • Caps and budgets are still prompt text, not code. Moving them into hooks is an open item.
  • Its default answer is often "don't use me", which can feel like a wasted step.
  • Its token estimates are optimistic: in 33 of the author's logged fleet runs, the median run used 1.6x its estimate.
  • Lasts one run. It holds no state across sessions; that is /dag's job.
Tool two

/bakeoff Two cooks, one frozen recipe, a blind taster

The pictureNobody may edit the recipe once the contest starts. Each cook works at a separate station. The taster sees two unlabelled cakes and a scorecard written before anyone baked. After three contests the house picks its method and the contest closes.

Under the hood: how a bakeoff is run
  • One shared plan, written onceA numbered task plan where each task has a files block, its interfaces and a verify step. Both arms build from it, into separate worktrees or branches, and never share a write target.
  • Arm A and Arm BArm A is the current default (in run 1, /graph with the Workflow tool). Arm B is any second builder. The recommended next challenger is a single-session control arm, because it tests whether orchestration helps at all.
  • Compared on anchors onlyTests that ran, the acceptance checks, defects found by a blind verifier that sees both outputs relabelled X and Y, judged twice with the labels swapped (added after run 1, which used one pass), wall clock, tokens, and how often a person had to step in.
  • When to use itLarge software builds: about 15 or more plan tasks, or several hours of work. Not research, audits or fixes.
  • It retiresAfter three runs per arm, the arm ahead becomes the default in /graph (a direction, not proof) and the command stops being needed.

p = 0.25The chance that one of two equally good arms wins all three runs by luck. Three runs can show a direction; they cannot crown a winner.
429 vs 115Coincident failures among five coding agents building from one spec, against what independence would predict. A shared plan makes both arms fail together.

Pros

  • Decides on anchors: tests that ran, frozen acceptance checks, and a blind verifier, run twice with the labels swapped, that cannot tell the arms apart.
  • The frozen plan makes the two arms comparable task by task.
  • Arm B is pluggable, so the same test can try a different harness, a different tool, or a plain single session.
  • It has an end: three runs, then the arm ahead becomes the default and the command retires.

Cons

  • Budgeted at roughly 2x one build, since everything is built twice (an estimate, not a measurement).
  • Three runs show direction only (p = 0.25 that one of two equal arms sweeps all three).
  • A shared plan makes both arms fail together (429 coincident failures observed against 115 predicted), so a bad plan hides the difference.
  • Only worth it for large builds; run 1 itself fell below that bar.
Tool three

/dag The recipe card and the manager's signature

The pictureThe card lists every step and ticks each one off, so a new shift reads the card instead of guessing. Before a plate leaves, the kitchen stops and the manager signs that exact plate. The signature works once. A second plate needs a second signature.

A DAG (directed acyclic graph) is a set of steps joined by arrows with no loops. A digest is a short fingerprint computed from file contents: change one byte and the fingerprint changes.

Under the hood: how /dag runs a job
  • A spec, dag.jsonNodes are commands the runner executes, tasks a person does by hand, and gates a person approves. Each node declares the files it reads, the files it writes, and any other place it writes.
  • State in plain filesdag.py keeps state on disk in a .dag/ folder and reruns only what changed. In a folder with a job, the first command is status, which prints each node's state and one NEXT line.
  • Approval only from the personThe person types /dag-approve at the prompt. The record holds a digest of the reviewed files and of each released effect, so editing either afterwards makes the approval stale.
  • An effect runs once per approvalEach effect node gets $DAG_EFFECT_KEY, the same for the same content, to pass as an idempotency key wherever the outside system accepts one.
  • The optional dag-gate modA Claude Code plugin that refuses /dag-approve when the model types it, and refuses the model's writes into .dag folders.

What it took from other tools, and what it left out

Five read-only GitHub API censuses, of 900 to 3,074 repositories each, found no project that combines a local runner on the Python standard library, human approval bound to content, and receipts. Most of the borrowed parts came from build tools, durable-execution engines and code review, not from agent frameworks.

Taken

  • Fingerprints of content and of the command itselfFrom DVC. A go-task issue shows the bug when the command is left out.
  • Early cutoffIf a rerun writes the same bytes, the steps after it stay untouched. From Shake, Salsa and Bazel.
  • Data edges and order-only edges as separate fieldsFrom Make, Moon and Dagu. The fake edge test, written into the schema.
  • Two steps writing one target is a plan-time errorFrom DVC and Ninja. The reverse test, written as code.
  • A typed answer to "why did this rerun?"From Snakemake and Cargo.
  • Atomic writes under a lock; a crash leaves "unknown"From redo, DVC and Pydantic AI. A crash never means "run the effect again".
  • Approvals bound to a digest, spent onceFrom Gerrit, gittuf and open-multi-agent.
  • Hash-chained receipts that state what they did not observeFrom Bernstein.

Left out

  • Copying full state at every stepMastra stored a 300 kB conversation as 135 MB.
  • Pickled checkpointsLangGraph's own threat model rates the deserialization risk as High.
  • A pause that reruns the paused nodeLangGraph restarts the node on resume; one user's payment went through twice.
  • CyclesThey invite recursion-limit loops. In /dag a repair is an edit to the spec.
  • A server database or daemonUsers said beads' move to Dolt made it unusable.
  • Sticky approvalsThe OpenAI Agents SDK keeps an approval across a resume.
  • An LLM writing the whole graph in one passPrompt2DAG measured 29.2% success for that, against 78.5% for its hybrid method.

Pros

  • Binds approval to a content digest and spends it once (the idea comes from Gerrit and gittuf).
  • Early cutoff: identical output leaves later steps alone, so reruns stay cheap.
  • Plain files and standard-library Python: no server, no database, no daemon.
  • Where a job stands is one command, status, never a reconstruction.
  • Tested: 57 tests for the runner and 50 for the dag-gate mod, all in the repo.

Cons

  • The guard reads command text; it is not a sandbox. The digest is public, so a process outside its view could still write an approval, and obfuscated code can evade a text check. It only holds in sessions that load the mod.
  • Adds ceremony that one-off work, notification-only jobs, or anything cheap to rerun does not need.
  • An approval proves which channel typed it, not who sat at the keyboard.
  • A receipt checks files on disk, not what the outside system received.
  • The Workflow tool takes no input mid-run, so a gate is a checkpoint: run to the gate, ask, run again.

Route a job

Start at the head chef. Most orders never leave one cook.

  1. Start with /graph. Planning costs only main-session tokens, and it often answers: keep the job in one session./graph
  2. Steps depend on each other, the job is small, or you do not yet know what you are looking for: use one steerable session in a worktree.one session
  3. Work that is wide, independent and checkable, with a parallel share p of at least 0.7: let /graph fan it out./graph
  4. A large build while the experiment is still open: build it twice, from one frozen plan./bakeoff
  5. Anything that has to survive a session or leave the machine becomes a /dag job: checks, a gate the person approves, then the merge, deploy or publish./dag

One state file per job. Inside one session, /graph's run-state.json is enough. Once a job crosses sessions or ends in an outside effect, its release steps move into a dag.json. Never track the same tasks in both: two stores kept in sync are a hidden edge. One recipe card per order, never two.

Install

The installer copies each skill into ~/.claude/skills/<name>/, where Claude Code picks up skills.

git clone https://github.com/wilsonwu-ai/claude-graph-skills && cd claude-graph-skills && ./install.sh

That installs all three. Or just one: ./install.sh graph. Needs Python 3.9+ on macOS or Linux, standard library only.

Setup details, the optional dag-gate mod, and each skill's own notes are in the README.
